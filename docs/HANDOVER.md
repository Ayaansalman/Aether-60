## 1. System Overview & The Safe Engineering Claim

### 1.1 Safe Engineering Claim (Blueprint Section 17)
As defined in `docs/DOCUMENT4_OUTLINE.md` (Section 1) and grounded in `docs/LIMITATIONS.md`:

> *"We built a prompt-to-browser-game prototype with a structured game representation, automated smoke tests, and a bounded repair loop."*

### 1.2 Core Architecture Pipeline
The end-to-end flow connects 5 contract-bounded stages:
```
[User Prompt] 
       │
       ▼
[LLM Planner / Mock Provider] (`aether-backend/services/orchestrator.py`)
       │ (JSON output adhering to GameIR v1.0)
       ▼
[Pydantic Schema Validator] (`aether-backend/services/validator.py`)
       │ (Clamps numeric bounds, validates enums & schemas)
       ▼
[Deterministic Phaser 3 Client] (`aether-frontend/src/game/ArenaScene.ts`)
       │ (Exposes `window.__AETHER_GAME__` test harness hook)
       ▼
[Automated Browser QA Runner] (`aether-backend/services/qa_runner.py`)
       │ (Executes 17 spec-level Playwright checks)
       ├─────────────────────────────────┐
       ▼ (All 17 checks PASS)            ▼ (Lethal / Unplayable failure)
[Terminal State: READY]           [Bounded Parameter Repair Agent] (`aether-backend/services/repair.py`)
                                         │ (Max 2 repair iterations; numeric patch only)
                                         └──► [Re-test via Browser QA Runner]
```

### 1.3 Single Archetype Family
The engine operates strictly on a single archetype family: **2D top-down arena survival** in an 800x600 pixel bounding box with omnidirectional `free_2d` movement. Second genres (platformers, flappy/gravity physics, horizontal-axis locks, 3D traversal, and multiplayer) are explicitly out of scope for the 60% milestone.

### 1.4 Division of Labour: Model Synthesis vs. Deterministic Engineering
To avoid hallucinations and maintain engineering stability, responsibilities are strictly partitioned:

| Subsystem Component | Generated by LLM Planner / Repair Agent | Built Deterministically by Us | Repo Implementation File |
|---|:---:|:---:|---|
| **High-level Game Specification** | **Yes** | No | `aether-backend/schemas/game_ir.py` |

## 2. Windows Setup from a Fresh Clone

Follow these exact steps in Windows PowerShell to set up a clean, working development environment.

### 2.1 Prerequisites
- **Operating System**: Windows 10 or Windows 11
- **Python**: Version 3.11.x (check with `python --version`)
- **Node.js**: Version 18.0+ or 20.0+ (check with `node --version` and `npm --version`)
- *Note*: If Node.js is installed in `C:\Program Files\nodejs` but not on your user PATH, run:
  ```powershell
  $env:PATH = "C:\Program Files\nodejs;" + $env:PATH
  ```

### 2.2 Fresh Clone Installation Steps

```powershell
# 1. Clone the repository and enter the directory
git clone <repository_url>
cd AETHER_V3

# 2. Set up Backend Python Virtual Environment
cd aether-backend
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
playwright install chromium
cd ..

# 3. Set up Frontend Node Dependencies
cd aether-frontend
npm ci
cd ..
```

### 2.3 Environment Secrets Configuration (`.env`)
The repository explicitly ignores `.env` in `.gitignore` to prevent secret leaks. **Never share API keys and never commit `.env` to git.**

```powershell
# Copy the provided template to create your local .env
copy .\aether-backend\.env.example .\aether-backend\.env
```

Open `aether-backend\.env` in an editor and enter your **own** personal Google AI Studio API key:
```dotenv
# Provider selection: 'mock' for offline testing, 'openai_compat' for Google AI Studio
MODEL_PROVIDER=openai_compat

# Your personal Google AI Studio Gemini API Key
MODEL_API_KEY=your_gemini_api_key_here

# Base URL for Gemini OpenAI-compatible endpoint
MODEL_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/

# Primary model selection
MODEL_NAME=gemini-3.5-flash-lite

# Automatic fallback chain for quota exhaustion (HTTP 429)
MODEL_FALLBACKS=gemini-3.7-flash,gemini-3.6-flash,gemini-3.5-flash-lite,gemini-3.1-flash-lite

# Request timeout in seconds
MODEL_TIMEOUT_SECONDS=60.0
```

### 2.4 How to Choose `MODEL_NAME` and `MODEL_FALLBACKS`
- **Recommended Primary Model (`MODEL_NAME=gemini-3.5-flash-lite`)**:
  - Validated during Run A evaluation (`docs/EVAL_RESULTS.md`): achieves 91.7% first-response schema validity, 100% theme honesty, and 45.8s median end-to-end latency (`docs/eval/eval_openai_compat_gemini-3.5-flash-lite_20261014_115528.json`; in Run D on upgraded engine, median was 47,020.5 ms in `docs/eval/eval_openai_compat_gemini-3.5-flash-lite_20261016_091754.json`; planner-only median in Phase 0 benchmark with gemini-3.8-flash was 17.3s in `docs/eval/planner_gemini-3.8-flash_benchmark.json`).
  - Demonstrates superior endpoint stability compared to heavier models.
- **Alternative Primary Model (`MODEL_NAME=gemini-3.8-flash`)**:
  - Higher reasoning capacity, but operates under stricter rate limits (15 RPM).
  - Run C timed out in both attempts (`docs/eval/eval_openai_compat_gemini-3.8-flash_20261014_120523.json` and `docs/eval/eval_openai_compat_gemini-3.8-flash_20261015_172236.json`), cause not established.
- **Configuring Fallback Chain (`MODEL_FALLBACKS`)**:
  - Supply a comma-separated list of fallback models (e.g. `gemini-3.7-flash,gemini-3.6-flash,gemini-3.5-flash-lite,gemini-3.1-flash-lite`).
  - If the primary model exhausts its per-minute or daily quota (HTTP 429), `openai_compat.py` switches to the next fallback model in the list.
  - To disable fallbacks (e.g. during isolated benchmark runs), set `MODEL_FALLBACKS=`.

### 4.2 Model Fallback Chain Mechanics
Implemented in `aether-backend/providers/openai_compat.py`:
1. When a model request returns an HTTP 429 quota exhaustion (daily/quota limit or unresolvable rate limit) or exhausts retryable 503/timeout attempts, the provider invokes `_trigger_fallback()`.
2. It transitions to the next available model specified in `MODEL_FALLBACKS`.
3. The active model is stored in `_PROCESS_ACTIVE_MODEL` across requests in the current process to prevent repeating failed calls.
4. Fallback occurrences are recorded in `agent_trace.jsonl` and exposed via the `GET /api/v1/health` endpoint.

### 4.3 Standardized Error Code Registry
Documented in `docs/api-contract.md` (Section 3):

| Error Code | HTTP Status | Root Cause & Pipeline Behavior |
|---|:---:|---|
| `PROMPT_INVALID` | `400` | User prompt was empty, whitespace-only, or exceeded 1200 characters. |
| `MODEL_TIMEOUT` | `504` | Model failed to respond within `MODEL_TIMEOUT_SECONDS` (default 60s). |
| `MODEL_HTTP_ERROR` | `502` | Upstream provider returned HTTP 5xx or unresolvable 429 after retries & fallback exhaustion. |
| `MODEL_OUTPUT_INVALID` | `422` | Output was invalid JSON or failed Pydantic validation after 2 retries. |
| `SPEC_UNSUPPORTED` | `422` | Spec requested unsupported mechanics outside 60% GameIR boundary. |
| `QA_CRASHED` | `500` | Headless Playwright subprocess crashed, timed out (>180s), or threw an unexpected exception. |
| `QA_FAILED` | `422` | Critical non-patchable check failed (e.g. canvas stalled, restart broke). |
| `REPAIR_LIMIT_REACHED` | `422` | Spec remained unplayable after maximum allowed repair iterations (2 repairs = 3 tests). |
| `GAME_NOT_FOUND` | `404` | Requested `game_id` was not found in SQLite store. |
| `INTERNAL_ERROR` | `500` | Backend restarted while job was in-flight, or uncaught server exception. |

## 5. Known Limitations & Remaining Human Tasks

### 5.1 Known Engineering Limitations
Detailed extensively in `docs/LIMITATIONS.md`:
1. **Single Genre / Archetype**: Strictly 2D top-down arena survival. Prompts requesting 3D, platformers, or racing are adapted to arena survival with explicit limitation disclosures.
2. **Bounded Enemy AI**: Maximum 2 enemy types per game; 5 deterministic AI behaviors (`chaser`, `bouncer`, `patroller`, `dasher`, `shooter`). No complex boids or multi-phase bosses.
3. **Parameter-Only Repair**: The repair agent tunes numeric attributes (speeds, health, counts, targets). It cannot generate new JavaScript/TypeScript code or rewrite client engine logic.
4. **Mechanical Sanity != Fun**: 17 Playwright checks are automated smoke checks verifying movement, velocity, collisions, win/loss reachability, and survival margins, but do not measure subjective fun or provide mathematical proof.
5. **Provider Rate Limits & Latency**: Free-tier Gemini endpoints require inter-prompt delays (5s–13s) to prevent HTTP 429 quota exhaustion.

## 6. How Ayaan's Separate QA Agent Connects

Ayaan's QA agent is an external, independently developed subsystem and is **currently separate and not part of this repository**.

To integrate or connect Ayaan's QA agent to AETHER in the future:
1. **Agreed API Contract Required**: Integration must proceed through a mutually agreed API contract (such as a standardized REST endpoint, webhook notification upon job completion, or shared JSON schema).
2. **Contract Boundaries**: The external agent can consume:
   - Validated game specifications via `GET /api/v1/games/{id}/spec`.
   - Playable game URLs formatted as `http://localhost:5173/play/{id}?test=1`.
   - The browser-side test harness hook `window.__AETHER_GAME__` (specified in `docs/QA_HOOK.md`).
3. **No Assumptions on Internals**: AETHER makes no assumptions regarding the internal implementation, machine learning architecture, or heuristics of Ayaan's QA agent. Any coupling will remain strictly bounded by formal HTTP or JSON interfaces.
